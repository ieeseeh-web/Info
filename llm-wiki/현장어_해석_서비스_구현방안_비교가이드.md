# 현장어(Field Jargon) 해석 서비스 구현 방안 비교 가이드

> MES-DevKG / LLM 위키 프로젝트 — 별칭 사전 기반 현장어→시스템 용어 변환 서비스 설계

---

## 1. 문제 정의

요청하신 절차를 다시 정리하면 다음과 같습니다.

1. **정규화**: 공백·대소문자·조사 제거
2. **사전 조회**: 별칭 사전에서 정확 일치 → 부분 일치 순으로 탐색
3. **하강(fallback) 체인**: 어근 조합(랏→lot + 홀드→hold) → 오타 보정(자모 분해 + 편집거리) → 의미 유사 폴백
4. **근거 명시**: 어느 단계에서 해석되었는지(검수됨 / 자동 수집 / 관련 추정)를 답변에 표기

이것은 학술적으로는 **엔터티 링킹(Entity Linking)의 후보 생성(candidate generation) + 명확화(disambiguation)** 문제이며, 검색 업계 용어로는 **동의어/별칭 확장을 포함한 사전 기반 검색(dictionary-based retrieval)**에 해당합니다. 이미 귀하의 프로젝트(dev-knowledge-graph)에서 정립한 `evidence_type`(LLM_EXTRACTED vs MENTION_MATCH) 구분 원칙과 정확히 같은 계열의 설계 문제이므로, 이 가이드는 그 원칙을 현장어 해석이라는 구체 기능에 적용하는 관점으로 작성했습니다.

핵심 참고: 학계에서는 엔터티 링킹의 후보 생성 방식을 표면형 일치(surface form matching), 별칭 사전 확장(alias dictionary expansion), 사전 확률 매칭(prior probability matching) 세 갈래로 구분하며, 표면형 일치에는 편집거리(Levenshtein), n-gram, 정규화 같은 휴리스틱이 쓰이고, 별칭 사전은 지식베이스 메타데이터(동의어, 리다이렉트 등)로 구축된다고 정리합니다(Alam et al., 2022, *Neural Entity Linking: A Survey*; Zhang et al., *PMC10280402*).

## 2. 구현 방식 5가지 비교

| 방식 | 핵심 원리 | 신규 은어 대응 | 설명가능성(근거) | 구현·운영 비용 | 적합한 단계 |
|---|---|---|---|---|---|
| A. 순수 규칙기반 사전+편집거리 | 정규화 후 문자열 매칭, Levenshtein/Jaro-Winkler | 낮음 (등록 필요) | 매우 높음 | 낮음 | 1~2단계 |
| B. 형태소분석 기반 정규화 | 형태소 분석기로 조사·어미 제거, 어근 결합 | 낮음~중간 | 높음 | 중간 (사전 튜닝 필요) | 1, 3단계 |
| C. 임베딩/벡터 의미 유사도 | 텍스트를 벡터로 인코딩 후 코사인 유사도 검색 | 높음 | 낮음 (근사치라 이유 설명 어려움) | 중간~높음 (벡터DB 운영) | 4단계(폴백) |
| D. LLM 직접 해석 | LLM에 현장어와 사전 후보를 주고 판단시킴 | 매우 높음 | 중간 (LLM reasoning 첨부 가능하나 검증 필요) | 높음 (호출 비용·지연) | 3~4단계 최후 폴백 |
| E. 하이브리드 캐스케이드 | A→B→C/D를 단계적으로 시도, 실패시에만 다음 단계 | 높음 | 매우 높음 (단계별 태깅) | 중간 (설계 복잡도↑, 런타임 비용↓) | 전체 |

**결론부터 말씀드리면, 귀하가 제시한 절차 자체가 이미 E(하이브리드 캐스케이드)이며, 이는 업계·학계 모두에서 권장되는 방향입니다.** 정보검색 분야에서 BM25(어휘 기반) 단독이나 벡터 검색 단독보다, 두 방식을 함께 쓰는 하이브리드 검색이 지속적으로 더 나은 성능을 보이는 것으로 보고됩니다 — 어휘 기반 검색은 정확한 식별자·코드명에 강하고, 벡터 검색은 표현이 다른 동의어에 강하기 때문입니다(Redis Engineering Blog, *Full-text search for RAG*; InfoQ, *Why Vector Search Alone Isn't Enough*). "랏홀드"처럼 특정 현장 코드성 용어는 어휘/사전 기반이 유리하고, 처음 보는 표현의 의미 추정은 임베딩·LLM이 유리한 것도 같은 논리입니다.

## 3. 단계별 기술 옵션 상세

### 3-1. 정규화 (공백·대소문자·조사 제거)

- **한국어 조사 제거**는 사실상 형태소 분석 문제입니다. 순수 정규식만으로는 "랏홀드는", "랏홀드가", "랏홀드를" 같은 변형을 완전히 걷어내기 어렵습니다.
- 옵션 비교:
  - **Mecab-ko**: 속도가 빠르고 대용량 처리에 유리하며, 띄어쓰기가 없는 문장에서도 안정적인 분석 성능을 보이는 것으로 알려져 있습니다. 다만 어간화(stemming) 기능은 제공하지 않습니다(velog, 한국어 형태소 분석기 비교 3편).
  - **Kiwi(kiwipiepy)**: 세종 품사 태그 체계 기반 분석기로, 자체적으로 **오타 교정과 띄어쓰기 오류 교정 기능을 내장**하고 있어(`typos='basic_with_continual'` 옵션), 3~4단계(오타 보정)까지 한 라이브러리로 커버할 수 있는 장점이 있습니다(디지털인문학 시리즈 위키독스; Kiwi 논문 - 통계적 언어 모델과 Skip-Bigram을 이용한 한국어 형태소 분석기 구현).
  - **KoNLPy(Komoran/Hannanum/Kkma/Okt)**: Okt(옛 Twitter)는 신조어·줄임말·비속어에 강해 현장어처럼 표준 사전에 없는 표현을 다루는 데 유리하지만, 전반적 정확도는 Mecab보다 낮게 보고됩니다.

> **권고**: 처리량이 크지 않은 질의응답형 서비스라면 Kiwi가 정규화+오타교정을 함께 해결해줘 설계가 단순해집니다. 대량 배치 처리(로그 전수 스캔 등)가 필요하면 Mecab-ko를 정규화 전용으로 쓰고 오타 교정은 별도 모듈로 분리하는 것이 유리합니다.

### 3-2. 별칭 사전 조회 (정확 일치 → 부분 일치)

두 갈래 구현 옵션이 있습니다.

- **애플리케이션 레벨 사전(해시맵/Trie)**: 별칭이 수천~수만 개 수준이면 자체 관리 사전(RDB 테이블 또는 인메모리 Trie/해시맵)으로 충분하고, 감사(audit)와 검수 워크플로를 붙이기 쉽습니다. 귀하의 `AI_DOC_LINK`/`alias-candidates` 스테이징 구조와 자연스럽게 연결됩니다.
- **검색엔진(Elasticsearch/OpenSearch) fuzzy query**: 별칭 수가 많거나 다른 텍스트 검색과 함께 서비스해야 한다면, Elasticsearch의 fuzzy 쿼리(내부적으로 Levenshtein 기반)와 n-gram 애널라이저를 조합해 "정확 일치 우선, 실패시 fuzzy" 랭킹을 엔진 레벨에서 구현할 수 있습니다. 이 경우 BM25 스코어를 근거값으로 함께 로깅하면 3항목(근거 명시)에 활용 가능합니다.

### 3-3. 어근 조합(랏→lot + 홀드→hold) / 오타 보정(자모 분해 + 편집거리)

- **자모 분해 기반 편집거리**는 한국어 특유의 문제로, 단순 음절 단위 Levenshtein보다 초성/중성/종성 단위로 쪼개 거리 계산을 하면 "혿드"↔"홀드"처럼 자모 하나 차이인 오타를 더 정밀하게 잡아낼 수 있습니다. 최근 딥러닝 기반 형태소 분석 연구에서도 한글 자모를 분리해 음절 단위로 입력함으로써 자모가 바뀌는 오타에 강건한 모델을 구축한 사례가 보고됩니다(카카오 Khaiii, 서대룡 등의 BiLSTM+CRF 연구 - Kiwi 논문 내 인용).
- **어근 조합**(복합어 분해: "랏홀드" → "lot" + "hold")은 사전 기반 룰(직접 정의한 형태소 결합 규칙)로 처리하는 것이 일반적이며, 완전 자동화보다는 SME(현업 전문가) 검수를 거쳐 별칭 후보로 승격시키는 반자동 방식이 오탐을 줄입니다 — 이는 귀하가 이미 채택한 "미연결 청크만 LLM 개념 추출 → 별칭 후보 생성 → SME 검수" 원칙과 동일한 패턴입니다.
- **실무 라이브러리**: Python 기준 RapidFuzz(순수 문자열 편집거리, 매우 빠름), 자모 분해는 `hangul-jamo`, `soynlp`(비지도 학습 기반 한국어 형태소 후보 추출, 신조어에 강함) 등이 실무에서 쓰입니다.

### 3-4. 의미 유사 폴백 (최종 하강 단계)

여기서부터는 임베딩/LLM 계열입니다.

- **임베딩 + 벡터 검색(귀하는 이미 Milvus 보유)**: 별칭 사전에 없는 완전히 낯선 현장어 표현을 그래도 "가장 가까운 시스템 용어"로 근사 매핑하는 데 씁니다. 다만 벡터 검색은 근사치 특성상 왜 그 결과가 나왔는지 설명하기 어렵고, 오탐이 나도 사람이 잘 못 잡아냅니다 — 그래서 "관련 추정" 등급으로 근거를 낮게 표기하는 것이 중요합니다.
- **하이브리드(BM25/사전 매칭 + 벡터) 랭킹 결합**: 업계에서는 Reciprocal Rank Fusion(RRF, 통상 k=60을 기본값으로 시작)으로 어휘 기반 스코어와 벡터 스코어를 결합하는 방식이 표준적으로 쓰이며, 이는 벡터 단독 대비 지속적으로 더 나은 성능을 보이는 것으로 보고됩니다(Redis, *Hybrid search for RAG*; PremAI, *Hybrid Search for RAG: BM25, SPLADE, and Vector Search Combined*). 귀하의 케이스에서는 "사전 부분일치 스코어 + 임베딩 유사도"를 RRF로 합쳐 최종 폴백 후보를 정렬하는 방식이 적용 가능합니다.
- **LLM 직접 해석**: 후보가 여러 개거나 문맥 의존적 중의성이 있을 때(예: "홀드"가 설비 홀드인지 로트 홀드인지), 문맥(대화 이력, 장비/CH# 등 슬롯)을 함께 LLM에 주고 최종 선택시키는 방식입니다. 최근 연구는 LLM이 단순 편집거리·자카드 유사도보다 관계(맥락) 정보를 활용해 모호한 매칭을 더 잘 해소할 수 있다고 보고하지만, 동시에 "무엇을 매칭으로 볼 것인가"라는 정의 자체의 모호성은 LLM으로도 완전히 해결되지 않는다고 지적합니다(Huang, 2024, *Disambiguate Entity Matching using Large Language Models through Relation Discovery*).

> **권고**: 귀하가 이미 정립한 3단계 게이트(①사전+부분일치 →②벡터 검색→③미해결 시 LLM 개념 추출)를 이 현장어 해석 기능에도 그대로 재사용하시면 아키텍처 일관성을 유지할 수 있습니다.

## 4. 데이터 모델링 옵션: 커스텀 스키마 vs SKOS 표준

별칭 사전 자체를 어떻게 모델링할지도 선택지가 있습니다.

- **커스텀 스키마(현재 방식)**: `AI_DOC_LINK`처럼 `evidence_type`(LLM_EXTRACTED/MENTION_MATCH) 필드를 직접 설계해 쓰는 방식. 도메인 특화 근거 등급(검수됨/자동수집/관련추정)을 자유롭게 정의할 수 있어 지금의 요구사항에 가장 잘 맞습니다.
- **SKOS(Simple Knowledge Organization System, W3C 권고안) 표준 모델**: 온톨로지 업계 표준으로, `skos:prefLabel`(표준 용어), `skos:altLabel`(동의어·약어·철자 변형), `skos:hiddenLabel`(검색에는 걸리되 화면에는 노출하지 않는 오탈자 변형) 세 가지 라벨을 상호 배타적으로 구분합니다(W3C, *SKOS Simple Knowledge Organization System Reference*). 특히 `skos:hiddenLabel`은 정의상 "철자가 틀린 표현을 포함해, 검색에는 걸리지만 화면 표시는 하지 않는 라벨"로 명시되어 있어, 요청하신 "오타 보정으로 해석된 항목"을 표준 어휘로 표현하는 데 정확히 들어맞습니다.

| | 커스텀 스키마 | SKOS |
|---|---|---|
| 근거 등급 표현력 | 자유도 높음 (도메인 맞춤) | prefLabel/altLabel/hiddenLabel 3단계로 제한적 |
| 외부 시스템 상호운용성 | 낮음 | 높음 (RDF 기반, 타 시소러스와 매핑 가능) |
| Neo4j 적재 난이도 | 낮음 (이미 익숙한 구조) | 중간 (RDF-속성그래프 변환 필요) |
| 기존 프로젝트와의 정합성 | 높음 | 추가 설계 필요 |

> **권고**: Neo4j 기반 그래프를 이미 운영 중이므로 SKOS를 전면 도입하기보다, **SKOS의 3단계 라벨 구분 개념만 차용**해 `evidence_type`의 하위 유형으로 `PREF/ALT/HIDDEN` 성격을 매핑해두면, 향후 표준 시소러스나 외부 용어집과 연계할 때 변환 비용을 줄일 수 있습니다.

## 5. 근거(provenance) 명시 설계

요청하신 "검수됨/자동 수집/관련 추정" 3단계 근거 표기는, 귀하가 이미 정립한 `evidence_type` 원칙(LLM_EXTRACTED vs MENTION_MATCH 구분, 근거 등급 A~D 정책 — llm-wiki 문서 참조)을 현장어 해석에 그대로 적용하면 됩니다. 제안 매핑:

| 절차 단계 | 근거 등급 (제안) |
|---|---|
| 사전 정확 일치 (SME가 등록한 별칭) | **검수됨** |
| 사전 부분 일치 / 어근 조합 규칙 매칭 | **검수됨** (규칙이 SME 승인된 경우) 또는 **자동 수집** (미승인 규칙) |
| 오타 보정(자모 편집거리)으로 매칭 | **자동 수집** |
| 임베딩 의미 유사도 폴백 | **관련 추정** |
| LLM 직접 해석 (미해결 최종 단계) | **관련 추정** (+ LLM reasoning 요약을 근거로 첨부) |

이렇게 하면 답변 시 "OO 용어로 해석함(근거: 자동 수집 — 오타 보정 단계)"처럼 단계 자체가 곧 근거 등급이 되어, 별도 신뢰도 계산 없이도 일관된 설명가능성을 확보할 수 있습니다.

```
   │
   ▼
[2] 별칭 사전 정확 일치 조회 (RDB/Trie, SME 검수 항목) ──hit──▶ 근거=검수됨
   │ miss
   ▼
[3] 별칭 사전 부분 일치 (fuzzy: RapidFuzz/Elasticsearch) ──hit──▶ 근거=검수됨/자동수집
   │ miss
   ▼
[4] 어근 조합 규칙 (랏→lot, 홀드→hold) ──hit──▶ 근거=자동수집(→SME 검수 후 승격 대상)
   │ miss
   ▼
[5] 자모 분해 편집거리 오타 보정 (hangul-jamo + RapidFuzz) ──hit──▶ 근거=자동수집
   │ miss
   ▼
[6] 임베딩 유사도 폴백 (Milvus, 기존 자산 재사용) + BM25 하이브리드(RRF) ──hit──▶ 근거=관련추정
   │ miss
   ▼
[7] LLM 최종 해석 (문맥 슬롯 포함) → 근거=관련추정 + reasoning 첨부
   │
   ▼
미해결 시 → alias-candidates 스테이징에 적재 → SME 검수 큐로 전달
```

이 구조는 귀하의 03-extraction-staging-architecture 문서에서 정립한 "질의시점 vs 배치시점 2-레인" 및 "선순환 루프"(미해결 질의 → 후보 생성 → 검수 → 사전 승격) 원칙과 그대로 맞물립니다. 즉 이번 현장어 해석 기능은 별도 신규 시스템이 아니라, 기존 스테이징 아키텍처의 **질의시점 레인에 캐스케이드 단계를 명시적으로 확장**한 것으로 설계하시는 것을 권고합니다.
