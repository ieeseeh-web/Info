Section 01

문제 정의와 설계 원칙

현장 대화에서 나오는 “홀드”, “랏홀드”, “챔버 다운”은 시스템 안 어디에도 그 문자열로 존재하지 않습니다. 실제로는 LOT_HOLD, mes_eqpmas_ext.resv_event_desc, CH# Down 같은 식별자에 대응됩니다. 이 간극을 메우는 작업은 도메인 용어 정규화와 엔터티 링킹(Entity Linking) 문제로 볼 수 있습니다. 실제 런타임에서는 후보 생성(candidate generation)뿐 아니라 중의성 해소(disambiguation)와 해석 거부(abstention)까지 포함해야 안전합니다.

엔터티 링킹 서베이는 후보 생성 방식을 세 갈래로 정리합니다 — ① 표면형 일치(surface form matching, 편집거리·n-gram·정규화 등 휴리스틱 사용), ② 별칭 사전 확장(alias dictionary expansion), ③ 사전 확률 매칭(prior probability). 서베이는 표면형 일치만으로는 “Big Blue → IBM”처럼 문자열이 전혀 겹치지 않는 별칭을 잡을 수 없다고 지적하며, 이것이 별칭 사전이 필요한 이유라고 설명합니다(Alam et al., 2022). 현장어는 “Big Blue” 유형이 압도적으로 많습니다 — “랏홀드”와 LOT_HOLD는 표면이 겹치지만, “걸렸다”와 HOLD_STATE=Y는 전혀 겹치지 않습니다.

Section 02

데이터 모델 — CSV에서 그래프까지

제시하신 컬럼 구조는 분류(Event_Rule / Process / Definition / Request / DML)에 따라 채워지는 하위 컬럼군이 달라지는 프레임(frame) 구조입니다. 이것을 하나의 평면 테이블로 두면 NULL이 80%인 희소 테이블이 되지만, 그래프로 옮기면 프레임별 노드로 자연스럽게 분해됩니다.

2-1. 프레임 판별 규칙

분류채워지는 컬럼그래프 표현
Definitiondefinition.subject / predicate / object(:Term)-[:ASSERTS]->(:Statement {s,p,o})
Processprocess.from / to / relation(:State)-[:TRANSITIONS_TO {relation}]->(:State)
Event_Ruleevent_rule.trigger / condition / action / result(:Trigger)-[:WHEN]->(:Condition)-[:THEN]->(:Action)-[:YIELDS]->(:Result)
Requestrequest.intent / target(:Intent)-[:TARGETS]->(:Term|:Column)
DMLdml.table / column / value / meaning(:Table)-[:HAS_COLUMN]->(:Column)-[:HAS_VALUE]->(:CodeValue {meaning})

예시 행 “Chamber Down 공통 로직 개선”은 Event_Rule 프레임이며, trigger = “CH# 단위 장비 Down 수행 중 특정 CH# FAIL 발생”, condition = “공통 로직 및 FLAG ON 상태”, action = “FAIL 여부와 무관하게 다음 CH# Down 수행”, result = “나머지 Chamber 정상 Down 수행”으로 4노드 체인이 됩니다. 여기서 현장어 해석이 붙는 지점은 trigger/condition 텍스트 안의 CH#, FLAG, Down 같은 토큰입니다.

2-2. Neo4j 스키마 DDL

CREATE CONSTRAINT term_id IF NOT EXISTS
FOR (t:Term) REQUIRE t.term_id IS UNIQUE;

CREATE CONSTRAINT alias_key IF NOT EXISTS
FOR (a:Alias) REQUIRE (a.surface_norm, a.scope) IS UNIQUE;

Neo4j에서 타입을 생략한 CREATE INDEX는 현재 range index이며 등가 비교(=)에 사용할 수 있습니다. 별도로 TEXT INDEX는 trigram 기반으로 CONTAINS·ENDS WITH 같은 문자열 부분 검색에 적합하고, full-text index는 Lucene 기반의 토큰화·랭킹·근사 검색에 사용합니다. 따라서 S2 정확 일치와 S3 근사/랭킹 검색을 같은 “B-tree 검색”으로 설명하지 않고 역할을 분리해야 합니다.

한글 토크나이징 주의

full-text analyzer는 설치 버전에 존재하는 이름을 먼저 db.index.fulltext.listAvailableAnalyzers()로 확인하십시오. 특정 환경에 cjk가 있다고 가정해 DDL에 하드코딩하면 배포 시 실패할 수 있습니다. 본 가이드는 토큰 경계를 보존한 surface_lex 또는 애플리케이션에서 생성한 n-gram 검색 필드를 저장하는 방식을 기본으로 권장합니다. 한글 검색 품질은 실제 별칭 골든셋으로 analyzer/토큰화 전략을 비교해 선택하십시오.

2-3. CSV 적재 (프레임 분기 포함)

Cypher · LOAD CSV 적재 스크립트 (발췌)

식별자 안정성

term_id는 표시명(용어)을 slug로 변환해 만들지 말고 ETL에서 한 번 발급한 불변 ID를 사용하십시오. 용어명이 바뀌어도 그래프 식별자가 바뀌지 않아야 별칭·검수이력·에이전트 캐시가 끊기지 않습니다.

LOAD CSV WITH HEADERS FROM 'file:///terms.csv' AS row
MERGE (t:Term {term_id: row.term_id})
  SET t.pref_label = row.용어,
      t.context    = row.문맥,
      t.frame      = row.분류,
      t.updated_at = datetime()

// ── Event_Rule 프레임 분기 ──────────────────────────
FOREACH (_ IN CASE WHEN row.분류 = 'Event_Rule' THEN [1] ELSE [] END |
  MERGE (tr:Trigger   {text: row.`event_rule.trigger`})
  MERGE (cd:Condition {text: row.`event_rule.condition`})
  MERGE (ac:Action    {text: row.`event_rule.action`})
  MERGE (rs:Result    {text: row.`event_rule.result`})
  MERGE (t)-[:HAS_FRAME]->(tr)
  MERGE (tr)-[:WHEN]->(cd)
  MERGE (cd)-[:THEN]->(ac)
  MERGE (ac)-[:YIELDS]->(rs)
)

// ── Process 프레임 분기 ─────────────────────────────
FOREACH (_ IN CASE WHEN row.분류 = 'Process' THEN [1] ELSE [] END |
  MERGE (f:State {text: row.`process.from`})
  MERGE (o:State {text: row.`process.to`})
  MERGE (t)-[:HAS_FRAME]->(f)
  MERGE (f)-[:TRANSITIONS_TO {relation: row.`process.relation`}]->(o)
)

// ── DML 프레임: 시스템 식별자 결정적 연결 ────────────
FOREACH (_ IN CASE WHEN row.`dml.table` IS NOT NULL THEN [1] ELSE [] END |
  MERGE (tb:Table  {name: toLower(row.`dml.table`)})
  MERGE (cl:Column {fqn: toLower(row.`dml.table`) + '.' + toLower(row.`dml.column`)})
  MERGE (tb)-[:HAS_COLUMN]->(cl)
  MERGE (t)-[:MAPS_TO {evidence: 'CURATED'}]->(cl)
);
문맥 컬럼의 이중 역할

문맥 컬럼(원문 서술)은 두 번 쓰입니다. ① S6 임베딩의 입력 텍스트, ② S4 미해결 시 LLM에 주는 근거 스니펫. 따라서 이 컬럼은 요약하지 말고 원문 그대로 보존해야 하며, 여기에 나오는 mes_eqpmas_ext.resv_event_desc 같은 식별자는 정규식으로 추출해 MENTIONS 관계로 자동 연결할 수 있습니다 — 이것이 가장 값싼 결정적 링크입니다.

Cypher · 문맥 텍스트에서 식별자 자동 링크

MATCH (t:Term) WHERE t.context IS NOT NULL
WITH t, [m IN apoc.text.regexGroups(t.context,
       '([a-z][a-z0-9_]{2,})\\.([a-z][a-z0-9_]{2,})') | toLower(m[0])] AS fqns
UNWIND fqns AS fqn
MATCH (c:Column {fqn: fqn})
MERGE (t)-[r:MENTIONS]->(c)
  SET r.evidence_type = 'MENTION_MATCH', r.grade = '검수됨';
Section 03

별칭 사전 계층과 SKOS 매핑

별칭 사전을 “문자열 → 문자열” 딕셔너리로 만들면 6개월 뒤 반드시 무너집니다. 별칭마다 출처·등급·유효범위·수명이 다르기 때문입니다. W3C 권고안인 SKOS는 이 문제를 이미 세 가지 라벨로 정리해두었습니다.

SKOS 명세에 따르면 skos:prefLabel, skos:altLabel, skos:hiddenLabel은 상호 배타적(pairwise disjoint) 속성입니다. altLabel은 두문자어·약어·철자 변형·불규칙 복수형 등 대체 라벨을 담고, 오탈자·검색 보조용 비표시 표기에는 hiddenLabel을 활용할 수 있으며, hiddenLabel은 화면 표시에서는 감추되 검색에는 활용할 수 있는 라벨로 정의됩니다(W3C SKOS Reference / skos.rdf).

이 프로젝트에의 적용

SKOS를 RDF로 전면 도입할 필요는 없습니다. Neo4j 속성 그래프를 그대로 쓰되 라벨 세 종류의 의미론만 차용하십시오. 그러면 “오타 보정으로 잡힌 별칭을 사전에 넣되 사용자에게는 정식 표기로 보여주지 않는다”는 요구가 표준 어휘 한 줄로 표현되고, 나중에 외부 시소러스와 연계할 때 변환 비용이 거의 없어집니다.

from kiwipiepy import Kiwi
import re, unicodedata

kiwi = Kiwi()
for w in ['랏홀드', '챔버다운', '엔드런', '예약다운']:
    kiwi.add_user_word(w, 'NNP', score=5.0)

DROP_TAGS = {'JKS','JKC','JKG','JKO','JKB','JKV','JKQ',
             'JX','JC','EF','EC','ETN','ETM','SF','SP'}

def normalize(text: str) -> dict:
    t = unicodedata.normalize('NFC', text).lower()
    t = re.sub(r'[-_/]+', ' ', t)
    t = re.sub(r'\s+', ' ', t).strip()

    # S1에서는 typos=...를 사용하지 않는다. 오타 후보 생성은 S5 책임.
    toks = kiwi.tokenize(t)
    kept = [tk.form for tk in toks if tk.tag not in DROP_TAGS]
    surface_lex = ' '.join(kept)
    surface_norm = re.sub(r'\s+', '', surface_lex)
    return {'surface_norm': surface_norm, 'surface_lex': surface_lex}

from rapidfuzz import process, fuzz

def partial_match(surface_lex, scope, score_cutoff):

               if a['scope'] in (scope, 'GLOBAL')]
    choices = [a['surface_lex'] for a in aliases]

“랏홀드” = “랏”(lot) + “홀드”(hold)처럼, 등록되지 않은 복합 현장어를 등록된 어근들의 조합으로 해석하는 단계입니다. 핵심은 어근 사전을 별칭 사전과 분리해 관리하는 것입니다.

Python · 어근 분해 및 조합 해석

# 어근 사전: 현장 음차 → 표준 토큰 (별칭 사전과 별개 테이블)
MORPH = {
  '랏':'LOT', '롯':'LOT', '로트':'LOT',
  '홀드':'HOLD', '홀딩':'HOLD',
  '챔버':'CHAMBER', '챔바':'CHAMBER', '씨에이치':'CHAMBER',
  '다운':'DOWN', '예약':'RESERVED', '해제':'RELEASE',
}
MAX_LEN = max(len(k) for k in MORPH)

def segment(s):
    """최장일치 우선 DP 분해. 전부 어근으로 덮이는 분해만 채택."""
    n = len(s); dp = [None]*(n+1); dp[0] = []
    for i in range(1, n+1):
        for L in range(min(MAX_LEN, i), 0, -1):
            piece = s[i-L:i]
            if dp[i-L] is not None and piece in MORPH:
                dp[i] = dp[i-L] + [MORPH[piece]]; break
    return dp[n]              # ['LOT','HOLD'] 또는 None

def resolve_by_morpheme(norm):
    parts = segment(norm)
    if not parts: return None
    # 조합 키를 Term의 canonical_key와 대조 (순서 무관 집합 비교 포함)
    return lookup_term_by_tokens(parts, order_sensitive=False)

S5

오타 보정 — 자모 분해 + 편집거리

확률적근거: 자동 수집오탐 주의

한글은 음절 단위 편집거리가 오타 심각도를 과대평가합니다. “홀그”와 “홀드”는 음절 단위로 거리 1(=2음절 중 50%)이지만, 자모 단위로는 ㅎㅗㄹㄱㅡ vs ㅎㅗㄹㄷㅡ로 거리 1(=5자모 중 20%)입니다. 자모 분해가 오타 판정을 훨씬 정확하게 만듭니다.

이 접근은 학계에서도 검증됐습니다 — 한글 자모를 분리해 음절 단위로 입력함으로써 자모가 바뀌는 오타에도 강건한 모델을 구축한 연구(BiLSTM+CRF)가 있으며, 카카오가 공개한 오픈소스 형태소 분석기 Khaiii 역시 유사한 아이디어에 기반합니다(Kiwi 논문 내 선행연구 정리).

Python · 자모 편집거리 매칭

from rapidfuzz.distance import DamerauLevenshtein
import jamo   # pip install jamo

def to_jamo(s):
    """한글은 호환 자모로 분해, 영숫자는 그대로 유지."""
    out = []
    for ch in s:
        if '가' <= ch <= '힣':
            out.append(jamo.j2hcj(jamo.h2j(ch)))
        else:
            out.append(ch)
    return ''.join(out)

def jamo_similarity(a, b):
    ja, jb = to_jamo(a), to_jamo(b)
    return DamerauLevenshtein.normalized_similarity(ja, jb)

# 키보드 인접성까지 가중하려면 zip 기반 보정이 아니라
# 실제 confusion matrix를 반영한 weighted edit-distance를 별도 구현한다.

def typo_correct(norm, theta=0.86):
    # 길이 필터로 후보 축소 후 정밀 계산 (전수 비교 회피)
    lo, hi = len(to_jamo(norm)) - 2, len(to_jamo(norm)) + 2
    cands = [a for a in ALIASES if lo <= len(a['jamo_key']) <= hi]
    scored = [(a, jamo_similarity(norm, a['surface_norm'])) for a in cands]
    best = max(scored, key=lambda x: x[1], default=(None, 0))
    return best if best[1] >= theta else None

짧은 토큰일수록 편집거리 한 글자의 상대 비중이 커집니다. 짧은 토큰은 false accept 위험이 특히 크므로 길이별 임계값 또는 S5 skip 정책을 두는 것이 안전합니다. 다만 0.90/0.84 같은 수치를 문서에 고정하지 말고 실제 오타·음성 케이스 골든셋으로 교정하십시오. “홀드”와 “볼드”처럼 한 자모 차이지만 의미가 완전히 다른 hard negative를 반드시 포함합니다.

선순환 루프

Cypher · 검수 대기 후보 조회 (SME 화면 백엔드)

MATCH (s:StagedAlias)
WHERE s.occurrence >= 2 AND s.status = 'PENDING'
OPTIONAL MATCH (s)-[:SUGGESTS]->(t:Term)
RETURN s.surface, s.origin_stage, s.evidence_type, s.occurrence,
       collect({term: t.pref_label, conf: s.confidence, why: s.rationale}) AS suggestions,
       s.sample_queries[..3] AS examples
ORDER BY s.occurrence DESC, s.first_seen ASC;

8-2. graphify의 위치

graphify는 코드베이스와 문서·SQL 스키마·설정·PDF를 질의 가능한 지식그래프로 만드는 도구입니다. 코드 파일은 tree-sitter 기반의 로컬 결정적 AST 파싱을 사용하지만, 문서·PDF·이미지의 semantic extraction은 설정한 AI backend를 사용할 수 있습니다. 따라서 “모든 입력이 항상 로컬 처리된다”고 표현하면 안 됩니다. 설치 시 PyPI 패키지명은 graphifyy(y 두 개)이고 CLI 명령은 graphify입니다.

본 프로젝트에서 유용한 지점은 세 가지입니다.

  • LAYER 3 자동 수확 — 코드 파일의 AST 경로는 로컬 결정적으로 처리할 수 있어 함수·클래스·참조 같은 심볼을 초기 적재원으로 쓰기 좋습니다. 반면 문서/PDF까지 함께 추출할 경우에는 선택한 AI backend의 데이터 경계를 별도로 검토하십시오.
  • --wiki 모드 — 위키피디아 스타일 마크다운 아티클과 index.md 진입점을 생성해, 에이전트가 파일을 읽는 것만으로 지식 기반을 항해할 수 있게 합니다. llm-wiki 구조의 entities/ 계층을 부트스트랩하는 데 그대로 쓸 수 있습니다.
  • MCP 서버 노출 — --mcp로 그래프를 도구화하면 query_graph, shortest_path 등을 에이전트가 직접 호출합니다. resolve_field_term이 반환한 term_id → 식별자 → 실제 코드 위치로 이어지는 멀티홉 탐색의 마지막 구간을 담당할 수 있습니다.
경계 설정

graphify는 LAYER 3(시스템 식별자·코드) 수확 도구로 한정하십시오. 현장어 별칭(LAYER 1)은 코드에 존재하지 않으므로 graphify로 얻을 수 없고, 얻으려 시도하면 코드 심볼과 현장어가 한 그래프에 섞여 §01의 “추론은 1→2에만” 원칙이 무너집니다. 또한 graphify-out/graph.json은 재생성 가능한 파생물이므로, Oracle을 진실 원천으로 유지하는 기존 원칙에 따라 Neo4j로 적재할 때 출처를 GRAPHIFY_AST로 태깅해 수기 입력과 구분하십시오.

9-2. 골든셋 구성

약 200건 규모는 부트스트랩 예시로 시작할 수 있지만 통계적 충분성을 보장하는 수치는 아닙니다. 초기 세트는 실제 트래픽 분포와 별도로 단계별 회귀를 드러내는 stratified set을 만들고, 운영 로그에서 지속적으로 확장하십시오.

  • 정확 일치로 풀려야 하는 것 40건 (S2 회귀 방지)
  • 어순·부분 변형 40건 (S3 θ 튜닝)
  • 복합 현장어 40건 (S4 어근 사전 커버리지)
  • 실제 발생한 오타 40건 (S5 θ 튜닝 — 반드시 진짜 로그에서 수집)
  • 서술형·의미 질의 20건 (S6 검증)
  • 해석되면 안 되는 것 20건 (음성 케이스 — 이게 없으면 θ를 계속 낮추게 됨)
음성 케이스의 중요성

“볼드체로 써줘”의 “볼드”가 LOT_HOLD로 해석되면 안 됩니다. 골든셋에 이런 해석 거부 케이스가 없으면 커버리지 지표만 보고 θ를 계속 낮추게 되고, 어느 순간 시스템이 모든 것을 아무것에나 매핑하기 시작합니다. 이것이 캐스케이드형 시스템의 전형적 붕괴 경로입니다.

9-3. RRF·가중치 튜닝 시점

RRF의 상수나 dense/sparse 가중치에는 도메인 독립적인 정답이 없습니다. Milvus는 현재 RRFRanker와 WeightedRanker를 제공하므로, 초기에는 RRF를 calibration-light baseline으로 두고 라벨된 질의가 쌓이면 동일한 validation set에서 weighted fusion과 비교하십시오.

평가할 때는 top-1 정확도만 보지 말고 Candidate Recall@K, false accept, top1–top2 margin, P95 지연을 함께 비교합니다. 필요하면 reranker를 추가하되, “라벨 50건이면 충분”, “항상 cross-encoder가 최선”, “하이브리드는 일정 비율 향상” 같은 수치는 이 문서의 고정 규칙으로 두지 않습니다. MES 자체 데이터로 개선폭과 비용을 검증한 뒤 채택합니다.
